N-19  GUI: toward a more standard, easy, intuitive interface
      Requested generically ("una GUI piu' standard, facile ed intuitiva");
      these are the concrete points actually observed hands-on this round,
      not a generic UX checklist - each names a specific place, not a
      principle.
      - The Series properties selector is a plain-text combo; each entry's
        series already has an actual plotted colour. A small colour swatch
        per row (matching MatplotlibColorCombo's own approach elsewhere)
        would make "which series is this" recognisable without opening it.
      - The activity rail (Data / Chart options / Series operations) is
        icon-only with tooltip-only labels - fine once learned, but nothing
        in the running app teaches a first-time user what the four icons
        are for beyond hovering each one. Worth checking whether a
        one-time label (or a "?" walkthrough) is worth the added chrome,
        given nav rail structure itself is being kept as-is per the
        Finder-sidebar discussion.

        _apply_source_dependent_enablement in import_data_dialog.py, run
        after every _build_columns_table since that rebuilds the per-column
        combos from scratch. Disabled rather than hidden - the row stays
        where it was instead of the panel reflowing under the pointer mid-
        preview. Left panel also grouped into labeled sections (Source /
        Read options / Columns), the same create_compact_section_title
        convention as the properties panels and the connect-database
        dialog, instead of one flat form.
        Also done in the same pass: ConnectDatabaseDialog gained "Use a
        query" (a SQL box swapped in for the table list via a QStackedWidget,
        validated with is_read_only_select so this cannot become a way to
        DELETE against someone else's database), threaded through as
        SERVER_DATABASE_QUERY_READERS / read_sqlite_query / read_from_link_
        source's query branch so "Update link" also replays a query-sourced
        import. And the web-source quick-pick gained its own "Web" row
        label plus Add source/Delete source buttons - add_user_web_source/
        remove_user_web_source in data_sources.py, backed by a
        get_user_web_sources/set_user_web_sources section in user.json,
        layered onto the bundled web_sources.json catalogue (WebDataSource.
        custom marks which is which; only a custom entry can be deleted).
      - Manual spacing (Figure properties) asks for six raw 0..1 fractions
        with no visual feedback - a live-updating preview, or drag handles
        on the chart itself, is the more standard way this kind of control
        is usually presented, though it is a real redesign, not a quick
        pass.

N-20  

      Broader, beyond the chart itself - things a data scientist, an
      engineer or a student doing coursework would reach for:
      - Notebook/script export: a figure's series are already SQL queries
        plus a style dict, which is most of a pandas+matplotlib script or a
        .ipynb cell already written - export it for handoff/reproducibility
        outside this app.
      - Unit-aware axes (pint): an axis label carries a unit, and a
        "convert units" action rescales the display without touching the
        underlying SQL - useful wherever engineering data mixes unit
        systems.
      - Uncertainty propagation: a series operation combining two series
        with error columns (A+-dA op B+-dB) via the standard propagation
        formulas, output as a value + error series pair.
      - A one-click "chart + operation reports -> PDF/HTML" bundle -
        formalizing what results_published/set_notes_html already produce
        per operation into one exportable document.
      - A small scripting console (Python or SQL) against the current
        project's repo, for the point where a power user iterates faster
        typing than clicking through dialogs - the same repo the series
        operations already use, just without a dialog in front of it.

P2-19 pysym: user-authored Python/symbolic series - a suggested design, not
      yet scoped or agreed
      The ask: a series operation where the user writes Python/symbolic
      (sympy-style) code instead of picking one of the built-in transforms,
      previews it against a chosen series, and applies it to both a chart
      series and a real table under a name the user gives it.
      Sketch:
      - Storage: an internal __pysym__ table (name, code, description,
        created/modified timestamps), the same pattern __import_links__ and
        __table_descriptors__ already use - one row per named snippet, so
        it can be reused across series/figures without retyping it.
      - Editing: a series_operations/pysym_dialog.py following the existing
        SeriesOperationDialogBase shape (source series picker, code editor,
        preview plot, Apply) - reuses P2-12's inline-preview plumbing once
        that lands, rather than a second copy of it.
      - Dual output: Apply both draws the result as a new series (the
        existing ResultSeriesSpec/generated_table_name path every operation
        already uses) and materializes it into a table under the name the
        user typed - the second half is new; nothing today lets a series
        operation name and create a persistent table of its own rather than
        an auto-named "_generated" one.
      - Security, the part this cannot skip: a .dhub file is explicitly
        documented elsewhere in this codebase as something that gets
        emailed and committed without a second thought (see why credentials
        never go in one, app/utils/data_sources.py). Embedding arbitrary
        executable Python in that same file is a materially bigger risk
        than the saved SQL queries it already carries - SQL against one's
        own tables is bounded, Python is not. Do not let __pysym__ code run
        on file open, ever, only on an explicit Apply/Run the user clicks
        for that specific snippet - the same trust model a saved query
        already has - and execute it against a restricted globals dict
        (numpy/pandas/math exposed, no import/open/os/subprocess) rather
        than a bare exec(). A one-time warning the first time a project
        with a non-empty __pysym__ table is opened, naming what that means,
        is worth doing even so - this is closer to a spreadsheet macro than
        to a saved filter.

P3-4  Function Creator - Developer menu stub added, design sketch below
      app/functions/user_functions.py already documents the whole contract
      a fit function needs (name/category/description/expression/p0/params/
      execute/initial_guess) and is scanned with no registration step
      (functions_scanner.py). The tool is a short form for those fields -
      name, LaTeX-ish expression string, parameter names/starting values,
      an execute(x, p) body - that stamps a new class into
      user_functions.py (or a sibling file in the same scanned folder) and
      opens it. Validate immediately after writing: import the file fresh
      and confirm functions_scanner picks up the new class, rather than
      letting a typo surface only the next time someone opens the Fit
      dialog.

P3-5  Edit Localization - Developer menu stub added, design sketch below
      A table of every msgid/msgstr in
      app/locales/it/LC_MESSAGES/datahub.po (i18n._parse_po already reads
      it), filterable to "missing only" using the exact scan
      test_localization.py already runs (walk every module's _()/tr()
      calls, diff against the catalogue) - which would have caught the 5
      currently-untranslated add.vertical/add.horizontal/add.annotation
      strings the moment they were written instead of at the next full
      test run. Needs a _write_po counterpart to i18n's existing
      _write_mo (only the compiled .mo writer exists today) that keeps
      comments and ordering stable enough for a real diff to stay
      readable - rewriting the whole file on every save would turn one
      changed string into a thousand-line diff.

P3-6  Series Operation Builder and Renderer Helper - Developer menu stubs
      added, design sketch below
      The same idea as Function Creator (P3-4) applied to the other two
      "drop a correctly-shaped class in a folder, no registration" spots:
      app/series_operations (series_operation_scanner.py,
      SeriesOperationDialogBase) and app/charts (axis_renderer_scanner.py,
      BaseAxisRenderer). Each is a short form - name, description, the
      required/optional roles, a Kwargs sketch - that stamps a template
      file into the right folder and opens it; the scanner does the actual
      wiring, so there is nothing to register by hand once the file is
      correctly shaped. Same validation step as P3-4: import the stamped
      file and confirm the relevant scanner discovers it before declaring
      success.
